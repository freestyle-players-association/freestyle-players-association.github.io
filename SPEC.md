# FPA Docs — SPEC.md

## Overview

Replace the existing Docusaurus site with a SvelteKit static site that serves the same
Markdown documentation. The site must be fully statically generated (no server-side
rendering at runtime), deployable to GitHub Pages, and require zero external services.

**Source repo:** https://github.com/freestyle-players-association/freestyle-players-association.github.io  
**Live site:** https://docs.freestyledisc.org  
**Docs content:** `/docs/` directory in the repo root (kept as-is, no migration needed)

## Navigation strategy

Navigation is derived **entirely from the filesystem**, not from frontmatter. This mirrors
what Docusaurus already does (`autogenerated` sidebar) and keeps the docs directory
maintenance-free from a nav perspective.

### Rules

- The `docs/` folder at the repo root is the content source.
- Top-level subdirectories become **sections** in the sidebar.
- Files within a subdirectory become **pages** within that section.
- Both `.md` and `.svelte` files are valid page sources. If both exist for the same slug
  (e.g. `event-progression.md` and `event-progression.svelte`), **the `.svelte` file wins**.
- Ordering is controlled by a **numeric prefix** on directory and file names
  (e.g. `01-competition-manual/`, `01-event-progression.md`). The prefix is stripped
  from display labels.
- Display labels come from the `title` field in each file's frontmatter. If `title` is
  absent, the label falls back to the filename with hyphens replaced by spaces,
  title-cased.
- A `_category_.md` file inside a directory may optionally provide a `title` for the
  section label (same fallback logic applies if absent).

### Required frontmatter (minimal)

```yaml
---
title: "Event Progression"   # required for display label override
---
```

No other frontmatter fields are required. The existing docs need no changes.

### Nav data generation

At **build time**, a SvelteKit server-side module (`src/lib/nav.ts`) reads the `docs/`
directory recursively using Node's `fs` module (available at build time in SvelteKit),
collects all `.md` and `.svelte` files, deduplicates by slug (`.svelte` wins), parses
frontmatter from `.md` files using `gray-matter`, and returns a typed navigation tree.
For `.svelte` pages without frontmatter, the title falls back to the filename. This tree
is consumed by the layout to render the sidebar and by each page to determine prev/next
links.

```ts
// Shape of the nav tree
type NavPage = {
  title: string;
  slug: string;        // e.g. "competition-manual/event-progression"
  href: string;        // e.g. "/docs/competition-manual/event-progression"
};

type NavSection = {
  title: string;
  slug: string;        // e.g. "competition-manual"
  pages: NavPage[];
};

type NavTree = NavSection[];
```

## Routing

| URL pattern | Description |
|---|---|
| `/` | Homepage (renders `docs/index.md` or a welcome page) |
| `/docs/[section]/[page]` | Individual doc page |
| `/docs/[section]` | Section index page (lists pages in section) |

SvelteKit's `prerender = true` must be set globally. All routes must be prerendered
at build time — there is no dynamic server.

## Page layout

The layout (`src/routes/+layout.svelte`) renders:

1. **Top navbar** — site logo/title on the left; dark mode toggle + external links (Events
   Calendar, FPA Site) on the right. Uses shadcn-svelte `NavigationMenu` or simple styled
   links. The dark mode toggle uses shadcn-svelte's `mode-watcher` package — add
   `<ModeWatcher />` to the root layout and use the `toggleMode` store where needed.
   The toggle button should use the `Sun` / `Moon` icons from `lucide-svelte`.
2. **Sidebar** — full nav tree rendered using shadcn-svelte `Accordion` or a custom
   collapsible list. The active page and its section are highlighted. On mobile, the
   sidebar is hidden behind a shadcn-svelte `Sheet` triggered by a hamburger button.
3. **Main content area** — rendered Markdown, constrained to a readable max-width.
4. **Prev/Next navigation** — footer links to adjacent pages within the same section,
   derived from the nav tree.

## Search

Pagefind is run as a **post-build step**. It indexes the static HTML output in `build/`.

### Setup

1. Add `pagefind` as a dev dependency.
2. Add a `postbuild` npm script:
   ```json
   "postbuild": "pagefind --site build"
   ```
3. Pagefind writes its index and JS bundle into `build/pagefind/`.
4. A `SearchDialog` Svelte component uses shadcn-svelte `Dialog` + `Command` (cmdk) to
   render the search UI. It dynamically imports Pagefind's JS bundle on open to avoid
   blocking page load.
5. The search trigger (a button in the navbar, keyboard shortcut `Cmd/Ctrl+K`) opens
   the dialog.

Pagefind requires no API keys, no external service, and no build-time configuration
beyond pointing it at the output directory.

## Markdown rendering and Svelte islands

mdsvex makes `.md` and `.svelte` files fully interchangeable as page sources. The
rendered output is identical regardless of which format produced it.

### mdsvex configuration (`svelte.config.js`)

- `extensions: ['.svelte', '.md']` — both file types are processed by SvelteKit
- Syntax highlighting via Shiki (mdsvex built-in), using a dual-theme config
  (`github-light` for light mode, `github-dark` for dark mode) so code blocks
  automatically follow the active theme without any JavaScript flash
- Custom components can be mapped to HTML elements if needed (e.g. a custom `<table>`
  wrapper for responsive scrolling)

### Svelte components inside Markdown

Any `.md` file can use a `<script>` block to import and render Svelte components inline.
The rest of the file remains plain Markdown:

```md
---
title: Scoring Calculator
---

Use the calculator below to estimate your score.

<script>
  import ScoringCalculator from '$lib/components/ScoringCalculator.svelte';
</script>

<ScoringCalculator />

Scores are calculated according to section 2.3 of the judging manual.
```

### `.svelte` pages with colocated Markdown

When a page needs more interactivity than a Markdown file can cleanly express, replace
it with a `.svelte` file at the same path. Markdown files can be colocated in the same
directory and imported as components:

```svelte
<!-- docs/competition-manual/scoring.svelte -->
<script>
  import Intro from './scoring-intro.md';
  import ScoringTable from '$lib/components/ScoringTable.svelte';
  import Notes from './scoring-notes.md';
</script>

<Intro />
<ScoringTable />
<Notes />
```

The colocated `.md` files used purely as imports (not as standalone pages) should be
prefixed with `_` (e.g. `_scoring-intro.md`) so the nav builder ignores them as
top-level pages. The nav builder must skip any file whose name starts with `_`.

### Summary of precedence

| Situation | File to create |
|---|---|
| Pure documentation | `.md` file |
| Doc with one interactive widget | `.md` file with imported Svelte component |
| Mostly interactive, some prose | `.svelte` file importing colocated `_fragment.md` files |
| Fully custom page | `.svelte` file with no Markdown |

Admonition blocks (`:::note`, `:::warning`, etc.) — if present in the docs — require a
remark plugin. Audit the docs for usage before implementing; if unused, skip.

## Deployment

GitHub Actions workflow (`.github/workflows/deploy.yml`) replaces the existing workflow:

```
1. Checkout repo
2. npm ci
3. npm run build          # SvelteKit static build
4. (postbuild) pagefind   # runs automatically via postbuild script
5. Deploy build/ to GitHub Pages via actions/deploy-pages
```

The `adapter-static` output goes to `build/` by default. The Pages deployment source
is the `build/` directory.

## Open questions for the implementer

1. **Numeric prefixes:** The existing `docs/` files may not yet use numeric prefixes for
   ordering. Audit the current directory structure and either add prefixes or implement
   an alternative ordering mechanism (e.g. a `sidebar_position` frontmatter field as
   fallback, consistent with Docusaurus conventions to avoid needing to rename files).
2. **`index.md` per section:** Docusaurus generates a category index page. Decide
   whether each section directory needs an `index.md`, or whether the section route
   auto-generates a page listing links to its children.
3. **Existing frontmatter:** The current docs use Docusaurus-specific frontmatter keys
   (e.g. `sidebar_position`, `sidebar_label`). The nav builder should handle these as
   fallbacks so no doc files need to be edited.
